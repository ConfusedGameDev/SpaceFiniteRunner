Orientation

Finite Runner Handbook

Every moving piece of the hover-ship police-chase runner: what it does, the rules it keeps and why, and every knob that tunes it — in the ScriptableObjects and in the in-game DEBUG menu.

The game in one paragraph

You fly a hover ship down a finite spline track with a police cruiser on your tail. One launch impulse gets you moving, the throttle holds you at cruise speed, and only boost orbs push you past it — where a passive bleed pulls you back down, so boosts must be chained. You must hit Light Speed (the level's speed objective) at least once, then leave the track by one of three end ramps over a void, before the countdown runs out. The patrol hunts you: it holds back, then commits to attack runs that turn into a button-mashing tug of war; win it and one shoulder press destroys the cruiser.

Where the numbers live

Every tunable lives in a ScriptableObject (SO) asset, never as a field on a manager. At runtime the game usually plays a clone of the asset so nothing is mutated on disk. The DEBUG menu (pause → DEBUG) edits either that clone or, for some pages, the asset itself. A value can pass through up to five layers before it reaches the game:

1 · SO assetThe authored value, e.g. Fighter_ShipDefinition.
2 · Runtime cloneCopied at run start; gameplay reads this.
3 · Store upgradesShip only: level multipliers applied to the clone.
4 · Debug override assetResources/FiniteRunner_*Debug with applyOnLoad ON stamps saved slider values over the clone.
5 · Debug menuLive slider edits during play.

Badges used in this handbook

SO Edit the asset in the Inspector (Odin sliders). Permanent, versioned.

DEBUG · CLONE Debug page edits the run clone; the value is saved into a *Debug override asset and re-applied next play while applyOnLoad is on.

DEBUG · ASSET Debug page writes straight into the SO asset — the change stays after you leave play mode. No undo switch.

RELOAD Takes effect only after RELOAD SCENE. LIVE applies immediately.

Conventions worth knowing

  • Speeds are stored in m/s; the UI shows km/h (× 3.6). Cruise 1000 m/s = 3600 km/h.
  • Distance from the track start is the authoritative coordinate for everything — never spline t.
  • The ship is a kinematic, cast-based surface follower, never a dynamic rigidbody. At Light Speed it covers ~36 m per physics step, so each tick is split into ≤ 4 m substeps and the world is read by PhysX queries, never by moving trigger volumes.
  • Domain reload is off: static state survives play sessions.

Other shipped choices that change the feel

  • No loops or tubes spawn. In PF_Track's feature table Jump is 100 %, Loop 0 %, Full Tube 0 %.
  • The track is dead straight: straightness 100 on the prefab and TrackDebug — so no sweeps, no banking and no flat sweeps appear.
  • Every plain straight is open (no walls either side): openStraightChance 1.0.
  • Mission 1's Light Speed is 3423 km/h, below cruise (3600 km/h) — holding the throttle alone meets it. Mission 2 asks 7500 km/h.
  • dashSinglePress is ON (one press dashes), startingLives is 10, timeLimitSeconds 180.

How to get back to authored values

Select the override asset in Assets/04.Data/Resources/ and untick applyOnLoad. The debug menu will turn it back on the next time you move one of its sliders. FiniteRunner_FeatureDebug ships with it already off.

Flow

A run, start to finish

A mission is a city chase level plus this escape run. The Store's START MISSION snapshots the wallet, plays the city, and the city hands off additively (a glitch transition) into the runner scene FiniteRunner_Test. Every other scene trip goes through LoadingScreen.

  1. Boot — GameManager.Awake resolves the level (session → serialized → default), resets objectives, sets the countdown to timeLimitSeconds, adds the runtime helpers to the ship, builds the run's ShipDefinition (clone × Store × ShipDebug), deals lives, snapshots the wallet, inits the patrol, camera, weather/FX, music and pause menu. TrackGenerator builds the first stretch and pulls the track length.
  2. Launch — one launch impulse from the track start; the throttle then holds cruise. The patrol starts startGap (548 m) behind at its base speed.
  3. Live run, every frame — objectives latch; patrol arrest → fail; countdown ticks (on real time during duel slow-mo, so slow-mo buys perception, not time); hull 0 → fail; open-edge falls respawn you further on at 85 % speed with a 3 s shield and the patrol held back ≥ 150 m.
  4. End of track — the verdict: took a ramp and objectives met → win; objectives met but no ramp → MissedRamp; objectives open → TooSlow. At the lip, a win beats a same-frame arrest.
  5. Win beat — MISSION ACCOMPLISHED slams in letter by letter; the camera plants at the lip and the ship flies on off the ramp (it never lands) for 2 s; music fades while the glitch ramps (0.8 s) and holds (0.4 s); then the Mission Complete panel counts up and pays the whole mission at the RANK slam.
  6. Loss beat — the patrol's attack is aborted, a life is spent (while hull is on), MISSION FAILED (or GAME OVER) slams in for 2 s + 0.5 s tear, then the GameOverScreen: reason, RETRY? YES / NO. On the last life: forfeit (wallet back to the mission-start snapshot, city clear dropped) and PRESS ANY BUTTON → Store.
  7. Retry — Restart() resets everything in place (timer, objectives, hull, camera, FX, track regenerated), keeps the lives count, relaunches ship and patrol. No scene reload.

Neither ending speaks an RPG line or prints HUD text — the banner is the whole message. Run start is counted on the first unpaused frame because Launch can fire up to three times per run.

System

The ship

A hover ship that rides any collider surface. Speed is the whole game: the throttle holds cruise, the brake slows, orbs push past cruise and a bleed pulls you back.

Rules & decisions

  • One launch impulse, then the throttle. W / RT accelerates toward cruise at thrust; releasing coasts down at coastDrag; S / LT brakes at brakeDecel. the player controls pace, orbs control peak speed.
  • Only orbs exceed cruise, and above cruise passiveDeceleration bleeds it back. There is no speed cap. boosts must be chained; coasting on one orb never wins.
  • Kinematic, never physics-driven. Each tick is split into ≤ 4 m substeps; ground is found with 5 probe rays, walls with sphere/box sweeps. at ~36 m per step, a dynamic body would tunnel through everything.
  • Grip is only tested on flat sweeps. Banked sweeps always hold. Grip = gripBase + gripPerSpeed · v; exceed it and you slide outward (losing slideSpeedLoss/s). danger is authored, not random.
  • Dash (shoulder buttons) is a lateral burst that costs half the meter (dashCost 0.5). Airborne, it's a barrel roll. Dashing into a wall is a slam (hull damage + glitch).
  • Falls cost time, not the run. Hang past an open edge for more than edgeOverhang (1 m) for edgeGraceSeconds (0.25 s) and you fall; after fallDurationSeconds you're placed back further down the track at 85 % of your speed, blinking and untouchable for 3 s with the patrol frozen. The countdown never stops.
  • Rolling respawn (respawnRollingStart ON): you fly the shield window under control. OFF: you stand still through it, then relaunch.
  • Hover height, bob and pitch wobble are purely visual.

Under the hood — ship components
  • HoverBody (01.Scripts/Ship/HoverBody.cs) — the movement model. Per substep: free steering → hull sweep → re-seat on the surface (5 probe rays; the ship's up is never smoothed) → wall clearance (sweep, slim-hull retry, KeepClear whiskers, slide along walls). Jump gravity is solved per flight so the ship lands airDistancePerSpeed × speed metres on.
  • HoverShip — input → movement, dash, barrel roll, stall, and the autopilot the duel uses to lock controls.
  • ShipMotor (Runner/Ship/ShipMotor.cs + .Physics.cs) — no longer simulates. Mirrors the HoverShip into track coordinates (TrackBody: distance, lateral, height, speed, state) and adds runner rules: loop gate, ramp boost, ramp side hit, tube return, end-of-track (Fall / TerminalFall / Escape), and the analytic laser sweep.
  • ShipRecovery — lost-ship detection, ballistic fall, respawn search and relaunch. Timers run in the fixed tick so pause freezes them.
  • ShipPickupSweeper — box-casts along each tick's path for orbs, repair orbs and coins; blind while OffTrack/Respawning.
  • ShipSettings (04.Data/Ship/Runner_ShipSettings.asset) — surface/guide/recovery tuning of the standalone ship: maxStepMeters 4, maxSubsteps 24, attachRange 6, coyoteMeters 3.9, hullRadius 2, climbAngle 45, airDistancePerSpeed 1.08, guideRefreshMeters 16, reverseSpeed 25… Its dash, fall, respawn and trail fields are overwritten every frame from GameSettings by RunnerShipSettingsSync — tune those in GameSettings, not here.

  • Run definition = ShipUpgradeApplier.BuildRunDefinition: clone → Store multipliers → ShipDebugSettings.ApplyTo. Sentinel fields (−1) in ShipDebug are skipped; the older fields (impulse, bleed, acceleration, weight) are always stamped.
System

The track

A finite spline road streamed ahead of you, ending in a straight walled run-up and three ramps side by side over a void.

Rules & decisions

  • Finite length per level (RunnerLevelDefinition.trackLengthMeters; 0 = GameSettings.trackLengthMeters). The HUD shows distance left. time AND distance are the limits.
  • Streamed: aheadDistance (1600 m) of finished road is kept ahead, road more than behindDistance (1500 m) back is culled. Knots are never removed.
  • Collisions come from the same pose function that places everything (TrackColliderBuilder, 120 m chunks). no per-feature special cases; the ship reads the world through physics queries.
  • A missing wall is always a real drop. Edges are open only on the outer side of a flat sweep or on an open straight.
  • Shape: elevation within a band, grade-limited; turns with rate/arc ranges; banking proportional to the turn. A share of sweeps is authored flat (no outer wall; grip is tested). Turn rates are derived from the grip formula v²/R ≤ gripBase + gripPerSpeed·v — keep turnArcMin ≥ 2 × turnRateMax.
  • The end: a pinned end-zone knot, then endRunUpMeters of straight, walled road with no features or pickups, then three end ramps with endRampGapMeters gaps between them. The outer two reach 0.5 m past the wall so hugging a wall still lands you on a ramp. End ramps give no boost and never land.
  • The last two segments (the settle margin) are never decorated or populated.

Under the hood — track code
  • TrackManager — the only thing that touches the spline: distance → pose, sections, bands, edges. GetLateralBand is the steering lane (where things are placed); GetRoadBand adds the banked shoulders (where the ship can be). IsEdgeOpen, HasEnd, EndDistance, EndZoneStart. On PF_Track: shoulderFraction 0.4844, shoulderRise 5.1 m (measured off the road-slab mesh). Knots live in container space — use WorldToKnotSpace.
  • TrackGenerator — streaming + feature placement: featureCursor → DecideFeature → AddSection before anything is placed beyond it. Spans are culled by their END. FinishTrack → CreateEndRamps. Each spawner runs a runtime clone with its own RNG.
  • TrackColliderBuilder — 120 m chunks, 4 road columns (10 m quads on curled tubes), walls only where the edge is closed, ramp wedges with outward flanks, loop chunks surface-only on layer 10, surface sunk by hover height. Debug toggle showMeshes draws them.
  • TrackGuide (IShipGuide) — projects world positions back to track distance with Newton steps from the last answer (keeps the right pass of a loop). assist 0.18, acquireScanMeters 4000. FindRespawn skips sections, flat sweeps, ramps, and never passes EndZoneStart.
System

Track features

Ramps, vertical loops, cylinder tubes and laser gates. Features are placed one at a time from a weighted table; laser gates come from their own spawner.

Ramps / jumps

  • Inside the run-up by more than entryMargin, you're committed.
  • Beside a ramp its edge is a wall: hitting it costs speed (sideHitSpeedLoss) and hull (wallSlamDamage).
  • At the lip: take-off boost (feature ×, × jumpStrength) and gravity solved so you land airDistancePerSpeed × speed metres on, clamped.
  • A ramp reserves a straight, level landing zone. Take-offs count for JumpCount objectives. The camera forces the Far view in the air.

Vertical loops 0 % today

  • A speed gate: the verdict is taken once at the entry. Required speed grows along the run (1200 km/h + 18 per 100 m, capped at 2900).
  • A loop is only placed if predicted speed ≥ required × (1 + gateHeadroom).
  • Fail = drop off the top onto the exit, lose 40 % speed; the patrol gains ground.
  • Cinematic side shot + slow-mo so the loop reads (~3.5 real seconds).

Cylinder tubes 0 % today

  • You run round the outside of a pipe; a ±180° band means full circle.
  • Steering × steeringFactor. Curl in/out over curlLength.
  • The last returnLength returns you to the centre line with steering and dash locked. No barriers; orbs spawn all round.

Laser gates

  • Emitter pairs whose beam covers 20–30 % of the road: single horizontal, vertical (weight 0 today), three stacked, or a flat spinning rotor. Always wavy today.
  • Steered round, never jumped. A hit costs laserDamage (30) hull and laserSpeedLoss (10 %) speed at once, plus smoke, rumble and shake. Once per pass.
  • Never on/near a ramp, its landing, a loop, a tube or the final run-up. Allowed on flat sweeps and open edges.
  • A beam destroys the patrol — the one hazard you can aim it at.

Lasers stay analytic (segment closest-approach against the ship's substep path), with no colliders — a moving trigger would miss at Light Speed.

Boost orbs are the only way past cruise. Repair orbs heal. Coins are money. Brake pads are retired.

Rules & decisions

The patrol

One police cruiser that drives the same physics as your ship, rubber-bands to your speed, and never gives up — outrun it and a fresh, faster one cuts in.

Rules & decisions

  • Same physics as the ship (a TrackBody driven by PatrolDriver). It steers for you, brakes for flat sweeps it can't hold, goes round ramps or jumps them, takes loops perfectly, keeps 6 m inside open edges — and can fall off. the chase reads as a rival pilot, not a scripted threat.
  • Rubber band: target speed = max(floor, your speed × rubberBand). The floor starts at baseSpeed and rises by ramp per second.
  • Boost share: it takes boostShare of every boost you collect, and orbBoostShare of orbs it picks up itself (which it uses up).
  • Redeploy: outrun it past the retire gap and a fresh cruiser drops in behind you at your speed × patrolRedeploySpeedFactor, which becomes the new floor and bumps escalation. coasting can never shake it. A fall, a laser kill or ending up too far ahead also redeploys, without raising the floor.
  • The end of the track takes every patrol that reaches it, for good.
  • Arrest: only sitting on your tail inside catchDistance without committing, for sustainedCatchSeconds. The fuse is held (not cleared) through the whole duel cycle; a cruiser ahead of you builds no tail time. With the duel off, the old proximity catch (within alongsideLateral) returns.
  • It freezes while you fall/respawn, while paused, and once you leave the end.

The patrol hunts you: it holds a standoff, commits to an attack run on your flank, takes your controls for a tug of war, and either shoves you off or gets destroyed by one shoulder press.

Rules & decisions

  • Forbidden ground: it never commits on a ramp or its landing, a loop, a tube, or the final run-up. Laser gates are deliberately allowed. the exchange must be about the duel, not a feature killing you.
  • Rear ram: from behind, within 8 m, 6 m across, closing > 15 m/s. Costs you 8 % speed (never hull), takes one point off its damage pool (max 3), which only weakens its next push — the pool never kills. A fresh cruiser arrives with a full pool.
  • Laser kill: a beam destroys the cruiser (within warn distance). No escalation.
  • Armed: a blue or purple orb arms you for 3 s (sparkle trail). The next exchange started inside the window skips the bar and goes straight to the kill. One orb, one finisher.
  • Escalation: tier scale = 1 + 0.15 × tier (cap 2). It divides the attack interval and multiplies the push (cap 1.8). Rises only on a kill or an outrun; resets on launch.
  • Slow-mo buys perception, not time: the countdown uses real time during the tug.
  • The mash button is fixed (gamepad X / key X). The finisher shows your own dash-shoulder binding.
  • The RPG message queue is held while an attack run is in progress.

What persists

DEBUG · CLONE pages

  • Sliders edit runtime clones; the authored SOs are never touched.

  • In a build: session only.

Tuning recipes

Start every session by deciding whether the debug overrides should be on. Then:

Easier run

  • timeLimitSeconds ↑
  • Level's ReachSpeed target ↓
  • powerUpSpeedBoost ↑ or passiveDeceleration ↓
  • endRampGapMeters ↓

Harder run

  • Speed orb spacing ↑ (fewer orbs)
  • passiveDeceleration ↑
  • openStraightChance ↑, straightness ↓ with unbankedSweepChance ↑
  • Laser density ↑, coverageBand ↑

More duels, more drama

  • commitIntervalSeconds ↓, attackRunCooldownSeconds ↓
  • encounterLookaheadMeters ↓ (commits on shorter clear road)
  • duelTimeScale ↓ (deeper slow-mo)

Kinder patrol

  • sustainedCatchSeconds ↑ (and check PatrolDebug)
  • tugPressValue ↑, tugPushFraction ↓
  • finisherWindowSeconds ↑
  • boostShare ↓

Longer / shorter mission

  • RunnerLevelDefinition.trackLengthMeters
  • Scale timeLimitSeconds with it
  • Untick TrackDebug's applyOnLoad or its 48 km wins

Bring back the showpieces

  • Feature table: Loop / Full Tube probability > 0
  • straightness < 100 for sweeps and banking
  • Loop gate: loopSpeedFloorKmh within reach of cruise
