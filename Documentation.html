SpaceFiniteRunner — Systems Documentation

Unity 6 (6000.7.0a3, URP 17) · two game prototypes in one project: a spline-based hover-ship endless runner and a procedurally generated city police-chase. This document maps every system, how the classes relate (UML), how the scenes are wired, how to extend each system, and what every tunable does.
How to read the diagrams UML diagrams are rendered with Mermaid (loaded from a CDN — open this file with an internet connection, or view the published copy). Arrow conventions used throughout: solid arrow = serialized/inspector reference (composition) · dashed arrow = runtime lookup (FindFirstObjectByType, singleton Instance, GetComponent) · circle-ended “subscribes” label = C# event subscription · “spawns” label = runtime instantiation · diamond “SO” label = consumes a ScriptableObject asset.

1. Project overview

The repository contains two playable prototypes that share one UI/FX foundation and hand off to each other at runtime:

  • Finite Runner Runner — a hover-ship launches with one speed impulse and constantly bleeds speed; boost orbs and brake pads on an endlessly streamed spline track are the only way to change speed. Win by reaching Light Speed before the countdown ends; lose if the rubber-banding police patrol catches up, the timer hits zero, or the ship stops.
  • Police Escape City — a physics-based car chase through an infinite, deterministically generated city (Kenney road kit), with a police fleet AI, traffic, street decoration, and an objective-driven level flow that glitch-transitions between scenes.
  • Shared foundations Shared — the themed menu framework (main menu, pause menu, debug pages, localization in four languages), the cheat-code system, gamepad haptics, and the fullscreen glitch / X-ray silhouette render features.

Project-wide rules
  • New Input System only — never the legacy Input class. Input is polled (there is no .inputactions asset).
  • Tunables live in ScriptableObjects in Assets/04.Data/, drawn with Odin attributes ([PropertyRange] sliders, [MinMaxSlider] bands, [InlineEditor] inlined into consumers). Add knobs there, not as hardcoded fields.
  • Runtime clones, never assets — systems that let the player/debug menu change values at runtime (ShipMotor, PolicePatrol) clone their definition asset first. City-chase settings are the deliberate exception: they are edited live and flushed to disk at menu commit points.
  • Spawnable systems are prefabs under Assets/03.Prefabs, pre-placed in scenes so they can be seen before entering play mode; code-built ones expose an Odin Rebuild Preview button.
  • Editor-only code goes in Editor/ subfolders with editor-only asmdefs.

3. Finite Runner — gameplay systems Runner

Code: Assets/01.Scripts/Runner/ · Scene: Assets/05.Scenes/FiniteRunner_Test.unity · Data: Assets/04.Data/FiniteRunner/

Core mechanic: the ship launches with a single speed impulse (ShipDefinition.initialImpulse) and constantly bleeds speed (passiveDeceleration). Boost orbs and brake pads on the track are the only way to change speed — there is no speed cap. The game is spline-based, not physics-based: the ship is moved kinematically along a SplineContainer; pads detect it via trigger colliders against its kinematic rigidbody.

Boot, per-frame loop, and the restart cycle. The lose line's onFinished is Restart, so the reset happens only after the message disappears; Restart() calls ClearMessages() first so a manual restart can't double-reset.

Pickup chain (the most-traveled path)

  1. SpeedPad.OnTriggerEnter → motor.AddSpeedImpulse(SpeedDelta) + static SpeedPad.Collected(pad, motor).
  2. ShipMotor queues definition.ScalePadEffect(raw) (divided by weight), blends it in at the ship's acceleration rate, and raises PadImpulse(raw).
  3. Subscribers fan out (see diagram above). GameManager.OnPadCollected shows the story line when pad.TierName == settings.messageOrbTierName (“Purple”).

Boost strength per orb = GameSettings.powerUpSpeedBoost × PadSpawnEntry.multiplier, then ÷ ShipDefinition.weight. Brakes ignore the multiplier and use PadDefinition.speedDelta directly.

Key invariants — do not break these
  • Spline knots are never removed during a run — distances must stay valid; only spawned objects are culled. RegenerateForRun() fully rebuilds between runs.
  • Nothing is placed on the trailing SettleMargin (2 × max segment length) — AutoSmooth reshapes those curves when the next knot lands.
  • Hover bob and banking apply only to the visual child; the root stays exactly on the flight line so trigger detection is unaffected.
  • Never mutate the ScriptableObject assets at runtime — ShipMotor/PolicePatrol work on clones; tiered orbs override per-instance via SetDefinition(def, delta, tint).
  • Speeds are stored in m/s; UI converts with × 3.6.

4. Police Escape — city-chase systems City

Code: Assets/01.Scripts/PoliceEscape/ · Scene: Assets/05.Scenes/CarTest.unity · Data: Assets/04.Data/InfiniteCity/

A physics-based (WheelCollider) car chase through an infinite, deterministically generated city. Five subsystems: city generation (City/), buildings (Population/), street props (Decoration/), the vehicle stack (Vehicles/), pursuit & traffic AI (AI/) — tied together by an objective-driven level flow (LevelManager) and a set of code-built HUDs (UI/).

4.1 City generation

Determinism is the foundation: every decision derives from globalSeed through DeterministicHash (FNV-1a, platform-stable — never string.GetHashCode). Arterial roads are a pure function of world cell coordinates, so neighbouring chunks agree without communicating. Each subsystem draws from its own salted RNG stream, so changing one never reshuffles the others:

Generation pipeline per chunk. RoadNetworkGenerator and the placers are pure/static — settings + chunk coordinate in, ChunkData out — which is what makes the city map screen able to generate chunks anywhere without touching the streamed world.

Pipeline order (per chunk)

  1. Carve arterials — hash of world cell coords (salts 101/202); they continue seamlessly across chunk borders.
  2. Carve connectors — interior secondary streets (connectorDensity, turnProbability for L-shapes), never touching borders.
  3. Repair dead ends (unless allowDeadEnds), then resolve 4-bit EdgeMask connections per cell.
  4. RoadFeaturePlacer (salt 606, ≥1 cell from borders): overpasses at arterial crossings (ramps → road-bridge deck → ramps; ground under decks becomes Reserved + pillar), forks (Y-splits on cell seams with SetCenterOffset so graph edges stay axis-aligned), multi-cell templates (3×3 roundabout, matched in 4 rotations).
  5. RoadGraph.RegisterChunk — ground nodes (level 0) + deck nodes (level 1). Neighbour rule = mutual connection; that's what links ramp↔deck and keeps a deck from leaking into the street beneath. TryGetNearestNode penalizes vertical distance ×3.
  6. BuildChunk — stamp pieces (salt 404). Every piece is sunk by RoadSurfaceHeight (lane height × scale) so the asphalt lane, not the pivot, lands at y = 0 on the chunk's ground slab. Flat tiles have no collider (they ride the slab); ramps/decks/pillars carry mesh colliders.
  7. CityPopulator.Populate (salt 505) — buildings on IsBuildable (Empty) cells only; Reserved is neither road nor lot.
  8. CityDecorator.Decorate (salt 707) — props on plain flat road tiles at curb height, facing the tile centre.
Streaming In play mode CityManager keeps a (2·loadRadiusInChunks+1)² block around the player (anchor = player car, else camera), unloading with hysteresis. All RNG decisions happen synchronously at build time — only Instantiate calls are queued (maxSpawnsPerFrame) — so a streamed chunk is bit-identical to an instantly built one. Generated objects carry DontSave flags and are always rebuilt from seed + settings.
Kenney kit facts (read off the FBX vertices — Unity mirrors the FBX X axis on import) road-straight runs E–W at yaw 0 · road-end opens West · road-bend connects N+E · road-slant-high climbs its lane 0.01→0.51 in one tile · road-bridge carries an N–S deck lane at 0.51 plus the E–W street underneath (includesUnderpass). Every height is a LANE height, never the tile's bounds top — the curb sits 0.01 native above the lane. The builder measures lanes by triangle area (widest flat up-facing surface) because the low-poly tiles have no vertex at the tile centre.

One physics sim (CarController), three drivers behind one interface. Police use the same CarConfig as the player; traffic shares it via TrafficSettings.carConfig. Suspension/friction are re-pushed every FixedUpdate (live tuning); mass/COM/substeps need ApplyConfig().
Vehicle-stack rules
  • Single player car — CarFactory.Spawn destroys only cars carrying a CarInput; AI cars belong to their managers.
  • Never teleport after Instantiate — rigidbody interpolation history overwrites a post-hoc move. Spawn at the final pose; all warps go through CarFactory.Teleport (which also notifies Cinemachine).
  • VehicleRigBuilder expects wheels named wheel-front-left/right, wheel-back-left/right; the CarController must be added before the driver component.
  • PatrolManager.FindPlayerCar() (a CarController with a CarInput) is the project-wide “who is the player” resolver — use it, don't roll your own.

PoliceCarInput.AiState. LevelManager reads State != Patrol as “hunting” for the EscapePolice objective; the minimap colors blips by the same enum. Both AI drivers share the driving core: steer = angle/maxSteerAngle, corner slowdown, 3-ray obstacle checks (Vehicle → brake, Wall → stop), stuck → timed reverse, and HardRecover() teleport after prolonged zero progress (never during Chase).

PatrolManager keeps targetPatrolCount cruisers alive on a 1 s tick: spawns on clear flat ground nodes inside spawnDistanceBand, despawns beyond despawnDistance. TrafficManager is the same pattern for civilians (VehicleRigBuilder-built from a weighted FBX pool): no perception or A* — wander only, plus a right-hand junction-yield whisker; work vehicles cycle random stops. Spawners only ever use flat ground nodes (Level == 0 && !IsRamp).

Cheat-code rules
  • B / East and Escape can never appear in a code — they are the menu's Back. CheatKey has no Escape; CheatButton has no East. The stick is deliberately not read.

  • A token from a different device than the buffer holds wipes the buffer first — two half-codes on different devices must never add up to a match.

6. How to extend each system

Recipes for the most likely additions. The common thread: add a ScriptableObject knob, subscribe to an existing event, or implement an existing interface — the architecture is built so new features rarely touch the core classes.

Runner Runner

Add a new pad / orb type

  1. Create a PadDefinition asset (Create → FiniteRunner → Pad Definition): set speedDelta (+boost / −brake), color, sizeMultiplier, and floatingOrb (hovering sphere on the flight line vs. flat pad).
  2. Add a PadSpawnEntry to TrackGenerator.spawnTable in the scene: name, optional prefab (falls back to the code-built primitive with a recolored material), the definition, a probability (sliders auto-rebalance to 100 %), a boost multiplier (× GameSettings.powerUpSpeedBoost), color, and sway amplitude/frequency for moving orbs.
  3. That's it — the streamer rolls the table once per spacing step. A prefab entry keeps its own materials and gets its colliders forced to triggers; a moving orb's spawn lateral is auto-clamped so its sway arc stays inside the track.
  4. To give the new tier a story line, set GameSettings.messageOrbTierName to the entry's name — GameManager listens to the static SpeedPad.Collected event and matches TierName.

Add a new gameplay tunable

Add the field to GameSettings (run rules), ShipDefinition (ship feel) or PatrolDefinition (chase feel) — never to GameManager. Give it an Odin [PropertyRange] with a hand-picked range, or a [MinMaxSlider] band with accessor properties (the patrolRedeployBand pattern) so gameplay code never touches .x/.y. If it should be debug-tweakable at runtime, mirror it in the matching *DebugSettings (CaptureFrom/ApplyTo) and add a DebugSliderRow in DebugMenuFactory.

Add a new feedback effect (shake, sound, particles…)

Subscribe to ShipMotor's events (PadImpulse, DashPerformed, WallHit, MeterFilled) or the static SpeedPad.Collected — the pattern ShakeOnPad and PadEffects use. Never poll or modify the motor. For world-space text use FloatingTextSystem.Instance.DisplayText(...); for dialogue use RpgMessageSystem.Instance.ShowMessage(...) (queued, one at a time, duplicates dropped with their onFinished still fired so callers can't stall).

Swap in a different input device (e.g. VR)

ShipMotor only reads ISteeringInput.SteerAxis (−1..+1) and IDashInput from a component on the same GameObject. Replace SteeringInput with your implementation — the motor is untouched.

Change what the track looks like

TrackDecorator owns the meshes: swap roadPrefab/barrierPrefab and their scale/spacing/yaw fields (authored for a 60 m track, stretched by trackWidth / 60). Use the material-override fields, not MaterialPropertyBlocks — MPB tints are unreliable with the SRP Batcher. Respect the streaming contract: anything you add must be spawned in DecorateUpTo and destroyed in CullBefore.

Police Escape City

Add a new road piece

  1. Add a RoadPieceDefinition entry to CityGenerationSettings.roadPieces: prefab, role (Standard pieces are the only ones socket-matched by TryPickPiece; Ramp/Deck/Pillar/Fork/HalfStraight are placed by the feature placer), connectionMask (EdgeMask at yaw 0 — remember Unity mirrors the FBX X axis), weight, rotationOffset, and the measured laneHeight.
  2. Multi-cell pieces: set footprintInCells > 1×1 and declare per-cell cellMasks (None = must be empty → becomes Reserved); the placer stamps it at the footprint centre wherever the grid matches, in any rotation, rolled by placeChance.
  3. Verify visually: Tools → Police Escape → Road Kit Showcase Scene lays every piece out with its sockets drawn live (RoadPieceSocketGizmo).
  4. For Kenney pieces prefer regenerating the whole list: Tools → Police Escape → Create Kenney Road Set measures lane heights and ramp chains off the FBX vertices and flips importer colliders on elevated pieces.

Add a new road feature (like overpasses/forks)

Extend RoadFeaturePlacer.Place — it must stay a pure function of settings + ChunkData, draw only from its salted RNG stream (salt 606, or claim a new salt), touch only interior cells (≥ BorderMargin from chunk borders), and record placement in ChunkData (features list / Reserved cells / upper connections) so RoadGraph and the stamper agree. Never read scene state from generation code.

Add a new building / decoration

Buildings: add a BuildingDefinition to the BuildingSet asset (footprint in cells, weight, jitters). Decorations: add a DecorationDefinition to the DecorationSet — choose IntersectionCorner (corner quads of 3+-socket tiles) or RoadEdge (socket-less tile edges) placement, and remember mass is the whole feel dial: lighter than the car (~1200 kg) flies on contact, heavier stops the car. The Kenney builder menu items rebuild the tuned sets from the kit folders.

Add a new AI driver

Implement ICarInput in a MonoBehaviour, then spawn with VehicleRigBuilder.Build<YourDriver>(modelPrefab, config, scale, pos, rot) — you get a fully rigged car with your driver reading its own logic and CarController doing the physics. Steal the driving core (waypoints from RoadGraph, corner slowdown, obstacle rays, stuck/reverse, HardRecover) from TrafficCarInput. Use PatrolManager.FindPlayerCar() to locate the player and CarFactory.Teleport for any warp.

Add a new level objective type

  1. Append to ObjectiveType (order is the save format — never reorder), add its knobs to LevelObjective with [ShowIf] on the type, and extend DefaultAccent/DefaultBriefing/ValueText/Summary.
  2. Implement evaluation in LevelManager.Evaluate; decide whether it's a state step (also extend StillHolds for AllMustHold mode) or a progress step (per-step runtime state goes in the private ObjectiveState, never on the asset).
  3. Add a display case to ObjectiveHud (+ a MenuTextId prefix, translated in all four languages) and, if it has an adjustable value, a row in CityDebugMenuFactory.BuildLevelTab.

“Go to” destinations are TargetObjects: root scene objects (chunks are streamed and destroyed) with a unique string id; snapToRoad slides them onto the nearest ground road cell once their chunk exists.

Screens: MenuScreen.Create(...) → SetTitle(MenuTextId) → AddRow<T>(MenuTextId); add new strings as MenuTextId entries with all four translations in MenuTextLibrary — never raw strings (debug/generated labels may use the string overload). New spawnable system (HouseWork M3 pattern)
